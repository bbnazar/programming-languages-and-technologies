## 2. Анализ требований и схема

Пользователи: `anna`, `boris` (тестовые учётные записи). Защищённый ресурс: заметки, каждый пользователь видит и удаляет только свои.

```
Браузер → POST /login → сервер проверяет логин и bcrypt-хеш
        → создаёт сессию, отправляет cookie (HttpOnly, SameSite=Lax)
        → GET /profile, GET /api/notes проверяют сессию → 200 или 401
        → DELETE /api/notes/:id → 403, если заметка чужая
        → POST /logout → сессия уничтожается, cookie удаляется
```

Выбран механизм **серверной сессии** (express-session + cookie), а не JWT: токен недоступен JavaScript и не хранится в localStorage.

## 4. Описание реализации
- **Сервер:** `POST /login` проверяет пустые поля (400) и пароль через `bcryptjs` (401), затем вызывает `session.regenerate()` (защита от фиксации сессии). `POST /logout` вызывает `session.destroy()` и удаляет cookie. Маршруты заметок защищены `requireAuth`, удаление проверяет владельца (403). Срок сессии 15 минут.
- **Клиент:** форма входа, приватный блок со списком заметок, сообщения об ошибках; клиент только отображает результат. При обновлении страницы запрашивается `/profile`, поэтому вошедший пользователь остаётся в системе.

## 7. Меры безопасности
- Пароли хранятся только как bcrypt-хеши; в коде только тестовые учётные записи.
- Cookie `HttpOnly` и `SameSite=Lax`; при HTTPS включить `Secure` (`COOKIE_SECURE=true`).
- Сессия пересоздаётся при входе, уничтожается при выходе.
- Права проверяются на сервере (401/403), а не скрытием элементов интерфейса.
- Текст заметок выводится через `textContent` (защита от XSS).
- Секрет сессии берётся из `SESSION_SECRET`; значение по умолчанию только для учебного запуска.
- Данные в памяти сбрасываются при перезапуске (допустимо для учебного прототипа).

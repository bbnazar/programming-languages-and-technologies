## 1. Цель
Реализовать вход/выход, разграничение доступа по ролям (admin/user) с проверкой на сервере, защищённое API управления пользователями и журнал событий аутентификации.

## 2. Анализ требований и схема

Роли: `admin` (управляет пользователями, видит журнал), `user` (только вход и свой профиль).

```
Браузер → POST /login → проверка bcrypt-хеша → сессия + cookie → запись LOGIN_OK / LOGIN_FAIL в журнал
        → /api/users, /api/logs: requireAuth (401) → requireRole('admin') (403)
        → POST /logout → запись LOGOUT, сессия уничтожена
```

## 4. Описание реализации
- **Сервер:** `requireAuth` даёт 401 без сессии, `requireRole('admin')` даёт 403 при недостатке прав; роль берётся из серверных данных, а не из запроса. Журнал фиксирует `LOGIN_OK`, `LOGIN_FAIL`, `LOGOUT` с временем, логином и IP (последние 200 записей). Защита от самоблокировки: нельзя менять свою роль и удалять себя. Пароль минимум 6 символов, логин уникален (409). Хеш пароля клиенту не отдаётся.
- **Клиент:** форма входа; после входа профиль и роль; для admin таблицы пользователей и журнала, форма создания. Для user панель скрыта, но сервер всё равно вернёт 403 (кнопка «Попробовать открыть журнал»).

## 7. Меры безопасности
- bcrypt-хеши, пароли не возвращаются через API.
- Cookie `HttpOnly`, `SameSite=Lax` (при HTTPS — `Secure`); `session.regenerate()` при входе.
- Роль проверяется на сервере; скрытие панели в интерфейсе — только удобство.
- Журнал фиксирует успешные и неудачные попытки входа и выходы (аудит).
- Защита от самоблокировки: нельзя удалить себя или снять свою роль admin.
- Данные выводятся через `textContent` (защита от XSS).
- Данные и журнал в памяти сбрасываются при перезапуске (учебный прототип).

## 8. Творческое задание
**Подтверждение выхода** (`confirm()`) и **индикатор оставшегося времени сессии.** Подтверждение защищает от случайного выхода, индикатор предупреждает об истечении сессии.
